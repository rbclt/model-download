# Security Design: u2-import-rules

This describes how this Unit meets the requirements in `security-requirements.md`. It uses the components in `logical-components.md`, the rules in `rules.md` (BR6.1 to BR6.4, BR7.1, BR7.2, BR9.1 to BR9.6, BR10.1 to BR10.3, BR11.1 to BR11.3), the steps in `functional-spec.md`, the technology in `tech-stack-decisions.md`, the targets in `performance-requirements.md`, `scalability-requirements.md`, `reliability-requirements.md`, and `observability-requirements.md`, and the boundaries in `contract-summary.md`. The security design of u1-import-slice (one role, closed permission list, encrypted private buckets, event bus policy, allow-list logging, SES prerequisites) is not changed and is not repeated. This document also settles the two points that the review of the NFR Requirements left open (NFR3.25 and the expiry claim of NFR4.19; the second is settled in `reliability-design.md`). The application still holds no secret of its own.

## Design Decisions

| Requirement | Design |
|-------------|--------|
| NFR3.17 No new permission | The steps of this Unit use only calls that the role of u1 already allows: `HeadObject` and `GetObject` of the marker, `ListBucket` with the three prefixes, `DeleteObject`, conditional `PutObject` for the second counter, `CreateMultipartUpload`, `UploadPartCopy`, `CompleteMultipartUpload`, `AbortMultipartUpload`, and `ListBucketMultipartUploads` (all of these are covered by the object and listing actions on `holding/*`, `models/*`, and `state/*` in the stack of u1). A test of the synthesised policy compares the list of actions and resources with the one of u1 and fails if it grows, and the search for `s3:*` and `Resource: *` stays |
| NFR3.18 20 of 50 emails | Two counters (see `scalability-design.md`): the `notices` counter stops at 20 and serves the rejection email and the already-stored email; the main counter stops at 30 and serves the failure email of an import that ran. This amends NFR3.16 of u1: the total is still at most 50 a day, now as 20 plus 30. The day is the UTC day. The notifier names the counter at each send, so an email cannot be counted in the wrong one by accident. The values are constants in the code (`NOTICE_EMAIL_LIMIT = 20`, `FAILURE_EMAIL_LIMIT = 30`) and the owner can change them |
| NFR3.19 No value from a rejected event | The rejection email is built by a function whose only inputs are the eventId, the eventTime, and the names of the failed fields (a fixed set of three names). It takes no free text from the event, so no value from the event can reach the email by construction. The acceptance of an eventId stays as u1 built it (any non-blank id of at most 256 characters), so this Unit narrows nothing. The email shows the eventId only when it matches the safe pattern of an event bus id (letters, digits, dot, underscore, colon, hyphen, at most 128 characters); otherwise it shows the importId, which is derived from it and always safe, and the subject uses the same choice. The eventTime is read from the `time` field of the envelope, parsed to a time, and written again by the code. If `time` is missing or does not parse, the message is still a start event and the email says that the time is not available (this replaces the words "or eventTime" in BR6.4). The log, the record, and the outcome of a rejected event use the same inputs |
| NFR3.20 No sender address stored | The sender address lives in the parsed event object only. The event objects (`StartEvent` and the new rejected-event object) are given `field(repr=False)` for the address, a change to `event.py` because u1's frozen dataclass shows it in its text form, and the log allow-list has no field that could hold it, so a call such as `log.info(..., senderEmail=...)` is dropped. The notifier receives it only to use it as the recipient of one send. The outcome stores roles, not addresses (BR10.3). A test plants an address and searches every log record, record, outcome, marker, and email text |
| NFR3.21 Marker content | The marker keeps the shape u1 built: the importId, the list of files with their sizes, and the completion time. It adds the model name and the exact version, which both passed the check of BR1.3. It holds nothing about the sender. This refines NFR3.21, which listed the importId, name, version, and time, by keeping the list of files that the reader rule of u1 needs |
| NFR3.22 State objects | The `state/` prefix lives in the holding bucket, which has encryption, TLS 1.2, and no public access (u1). The new counter object and the records need no new setting. The expiry after 30 days already applies |
| NFR3.23 Cleaned names | One function, the `clean_file_name` of u1 (control characters replaced, cut to 200 characters), is used for finding file names and leftover locations. A leftover location is the key inside its bucket, never a value from a file |
| NFR3.24 Deletion bounds | The removal builds its prefix only with `final_prefix(model_name, exact_version)` of u1, which returns `models/<name in lowercase>/<version>/` and ends in a slash. Both inputs passed BR1.3 before. The trailing slash is what keeps `models/org/model/` from matching `models/org/model2/`. The removal lists that prefix, never anything above it, and deletes only keys the listing returned. It deletes only when the folder has no marker or the marker was written by this import (BR9.2). Tests keep a sibling version, a sibling model with a longer name, and a folder with a marker of another import, and check that none is touched |
| NFR3.25 `_COMPLETE` and unreadable markers | See "Settled Here" below |
| NFR3.26 Clock | `Deadline` and every time in a record or an email come from the injected clock. No time is read from the event except the eventTime that the bus set, which is only shown, never used to decide anything |

## Settled Here: The `_COMPLETE` File and the Unreadable Marker (NFR3.25)

These results were left open by `security-requirements.md`. They are set as follows.

1. **A model file named `_COMPLETE`.** The check of the file listing (the path checks of BR1.3, run before any download) fails the import when a path equals `_COMPLETE` with letters compared without case. The plain reason is "a file of the model is named _COMPLETE". The import is a failed step with nothing to remove, and the failure email goes out. Only the path at the root of the version folder collides with the marker key; a file such as `sub/_COMPLETE` is ordinary. The check of u1's keep step (`KeepError`, "a file of the model is named _COMPLETE") stays as a second line of defence. A planted file can therefore never be copied to the final location.
2. **A marker that exists but cannot be read.** Two cases are kept apart. If the check itself fails (the `HEAD` or the `GET` of the marker returns an error other than "not found", for example a throttle or a timeout), the check cannot be made, which BR7.1 treats as a failed step with the failure email: nothing is refused, because the marker may be this import's own. Only when the body arrived and it is not a JSON object, or has no `importId` of the expected pattern, is it treated as a model stored by another import: the event is refused as already stored, nothing is downloaded or overwritten, and the log gets one record `marker_unreadable` with no content. The email reason is "this model version is already stored; its completion marker could not be read, so the team should check it". The marker is never deleted by this path.
3. **In the removal.** (BR9.2) The marker is read first and is deleted only when it holds this import's importId, with 3 tries; if it stays, it is reported as the first Leftover. A marker with another importId is left alone and is not a leftover, as the rule says. A marker that cannot be read or fetched is also left alone, but it is reported as a Leftover (kind object, area final-location, location the marker key), so removalComplete is false and the email tells the team. The whole final-location part runs only when the keep step had started writing (see `reliability-design.md`).
4. **The invariant.** removalComplete is true only when no object that this import wrote remains in the final location. The one stated exception is the race of BR9.2, where a complete copy of another import appeared and the files in the folder belong to a complete stored model.
5. **Tests.** A model with a root file `_COMPLETE` fails before the download. A damaged marker, a marker that is not JSON, and a marker without importId are each refused at the front door and not deleted. A damaged marker at removal time is reported as a Leftover.

## Threats and Controls

| Threat | Control in this design |
|--------|------------------------|
| A burst of bad events sends mail to many addresses or uses up the failure emails | Two counters, 20 and 30 a day (NFR3.18); only permitted identities can send events (u1) |
| A bad event carries a secret or a personal value that is echoed | The rejection email, the log line, the record, and the outcome take only the eventId, the eventTime, and field names (NFR3.19) |
| Header injection or an odd recipient through the sender address | The address passed the strict pattern of u1 (NFR3.14) before it was used as a recipient; it is never put in a subject or a header by this code, and the subject of a rejection email holds only a checked eventId |
| The removal deletes another model or version | Prefix built from checked names with a trailing slash; the folder is touched only when it has no marker or has this import's marker (NFR3.24) |
| A hostile model plants a file named like the marker | Failed before any download (NFR3.25 item 1); second check in the keep step |
| A damaged or foreign marker makes the application delete or overwrite a model | The event is refused and nothing is deleted (item 2); a removal leaves it and reports it (item 3) |
| The sender address leaks through a log, record, outcome, or marker | Masked in the event object; no allow-list field for it; tests search for it (NFR3.20, NFR3.21) |
| The stored-model email is used to find out which models exist | Only identities of the account that may send events can ask; the answer goes to the sender address given in the event and to the team. The owner accepted any well-formed sender address in u1 (Q4). Not mitigated further |
| A stolen worker role | Unchanged from u1: it reaches only the three prefixes, the one queue, SES from one identity, and logs |

## Assumptions & Open Questions

- [assumption] Treating an unreadable marker as "already stored" is the safe choice because a model is complete only when the application wrote the marker last, and only another writer can leave a damaged one. The team can remove such a marker by hand after checking it.
- [assumption] The ids that EventBridge creates are in UUID form, which fits the safe pattern, so the subject normally shows the eventId. The fallback to the importId only matters for a hand-made envelope.
- Open question: Who reads the final location later, and does the reader follow the marker rule of u1? Still open since u1; the owner names the reader before the model is used.
