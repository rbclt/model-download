### Suggestions

- AC2.1.4 (a smaller model ends inside 6 hours) is mapped only to the rules that enforce the limit (BR8.1, BR8.2, BR8.4). Nothing in the design says what keeps a 16 GB import fast. Add a measurable expectation, or mark the row as met in NFR Design.
- BR9.2 relies on "the single-import queue should prevent" a second import running at the same time. If the queue's visibility timeout is shorter than a long import, the same message can run twice and the marker-less delete could remove files that another run is still writing. Confirm the timeout in Infrastructure Design.
- Event publishers are not authenticated (open item R-07 in u1). BR6.2 widens it: any well-formed sender address in a bad event now receives an email. Decide who may publish the event.

### Summary

The design is largely complete and consistent with the contract, but it cannot be built without guessing in five places: redelivery after the marker, deadline checks inside a running transfer, the clash with u1's duplicate check, everything that happens after the marker is written, and a failed marker delete. The importId derivation also does not match the u1 rule it cites.
