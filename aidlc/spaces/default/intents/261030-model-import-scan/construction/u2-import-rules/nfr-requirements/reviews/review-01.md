### Suggestions

- NFR4.16 describes a failed import that leaves a complete model in the final location, with the outcome named removed-with-email or removed-email-failed. Inception NFR4 says "never both". Say in NFR4.16 that this case deviates from that wording and from FR5.2, and that the email carries the warning.
- BR9.2 deletes every object in a version folder that has no marker. A model stored by u1 before the marker existed would look unstored. If any real import happened under u1, add a note on how such folders are treated. If none did, say so.
- NFR3.19 covers the rejection email only. The already-stored email (BR7.2) also goes to any well-formed sender address and shows the model name, version, and final path. Add it to the data protection or threat table, or record it as accepted under the u1 Q4 decision.
- The threat table could cite NFR3.14 (header-safe sender address) as the reason a rejection email cannot be turned into header injection.
- NFR1.10 rests on an unmeasured copy time for a file up to 5 GiB. The assumption is flagged; keep it as an input for the first real import.

### Summary

The detailed requirements cover NFR1 to NFR6 with measurable targets that agree with the approved Functional Design numbers. Two Major gaps remain: the `_COMPLETE` file and unreadable marker case is left without a testable result, and NFR4.19 overstates expiry for files in the final location. Fix both at the gate; the rest are wording and consistency points.
