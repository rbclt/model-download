# Unit Test Instructions: u1-import-slice

How to run the tests of this Unit. The strategy is Standard: 5 to 8 tests for each building block, plus integration tests at the key boundaries and one end-to-end test (`code-generation-plan.md`). The team writes each layer first and then its tests (test-after).

## Setup

1. Python 3.12 is the target. This machine has Python 3.13.2; the code avoids anything that differs between the two, and the pipeline runs 3.12.
2. Create a virtual environment and install the project with its test tools:

```text
python -m venv .venv
.venv\Scripts\python -m pip install -e ".[dev]"
```

3. The test tools are pytest, pytest-cov, moto (AWS stand-ins for S3, SQS, SES), respx (a stand-in for the Hugging Face site), Black, and Ruff, all pinned in `pyproject.toml`. The CDK tests also need `aws-cdk-lib`, which `.[dev]` installs. The CDK command-line tool is not needed to run the tests.

## Commands for this Unit

Run the tests of this Unit only (the first run, before the coverage check):

```text
.venv\Scripts\python -m pytest tests/unit tests/integration tests/e2e tests/infra -q
```

Run the same tests with a coverage report for this Unit's code (no threshold, so a low number on one Unit never stops the run):

```text
.venv\Scripts\python -m pytest tests/unit tests/integration tests/e2e tests/infra -q --cov=src/model_import --cov=infra --cov-report=term-missing
```

Format and lint checks:

```text
.venv\Scripts\python -m black --check src infra tests app.py
.venv\Scripts\python -m ruff check src infra tests app.py
```

The project check recorded for every Unit is `python -m pytest --cov --cov-fail-under=80`, run from the project root with the virtual environment active. It checks the 80 percent line-coverage floor on the whole suite.

## Expected Coverage

- The floor is 80 percent of lines for the whole project (`NFR6.1`). Build and Test checks it on the full suite; a run of this Unit's tests alone does not judge it, so the threshold is not part of the first command above.
- Target for this Unit's own code: 85 percent or more, because the Unit holds all the code at this stage.
- The threshold is set in `pyproject.toml` for the project check and is never lowered to make a run pass.

## Mocking and Stand-ins

- AWS services: moto, with a fresh set of resources for every test through fixtures. No test calls a real AWS account.
- Hugging Face: respx routes for the listing and file URLs; large files are simulated with generated bytes of a small size and a size override, never with real downloads.
- Time: retry waits and the watchdog use a fake clock so no test sleeps for real.
- Secrets in tests: planted values are fake and built in the test (for example an access key shaped string split in two parts) so the repository scan of the pipeline does not flag the test files.

## Test Data

- Fake models are built in the test: a few small text files, one valid `.safetensors` header, and optional `.bin` files.
- No test data is stored outside `tests/`.

## Assumptions & Open Questions

- [assumption] moto supports every S3, SQS, and SES call the code uses, including conditional create. If a call is not supported, the test uses a small stand-in object for that call and says so in the test.
- Open question: Whether a real end-to-end run against Hugging Face is run by hand once the deploy-time settings exist (dependency D3). The automated suite never does.
