> R-01 Reviewer note: The Message Life Cycle table in reliability-design.md now covers every case: 15-minute visibility renewed every 5 minutes, delete after the outcome object is written, delete for a bad event, visibility 0 before a non-zero exit on a caught error, SIGTERM during an import, or the watchdog, a hard crash that frees the group in 15 to 20 minutes, and the one accepted false-alert window. The Recovery text no longer promises an immediate restart. A small leftover is listed under the new stale-text finding: the "outcome already exists" check on receive can never be reached by a redelivered message, because max receive count 1 sends it to the dead-letter queue first.

> R-02 Reviewer note: The NFR3.4 row now lists exact actions and resources: object actions on holding, models, and state; ListBucket and ListBucketMultipartUploads by prefix; the three queue actions on the queue ARN; ecs:UpdateTaskProtection on this cluster; ses:SendEmail with from-address and configuration-set conditions; log stream writes; no metrics permission; and the isolation test covers state. One build trap remains (new finding on missing-key lookups).

> R-03 Reviewer note: Removal deletes the marker first, nothing is written after the marker except the outcome, readers read only the files listed in the marker and compare sizes, and the non-expiry of unfinished files in models/ is recorded as a change to NFR4.2. A marker can no longer outlive its files.

> R-04 Reviewer note: NFR3.16 now keeps a durable per-day counter object under state/counters with a conditional write on the ETag, counts every attempt, refuses the 51st, and writes one log record with event email_limit_reached. Signal (e) is a metric filter on that record with a 5-minute period, and the role list has the permissions. Small gaps are in the new finding on the counter.

> R-05 Reviewer note: Most of it is fixed: protection is set on start with an 8-hour expiry and renewed, the watchdog exits non-zero, SIGTERM when idle exits 0, a missing metric counts as no messages, and the change to NFR1.8 is recorded. The gap: protection is released after 2 idle minutes while the worker keeps polling, and the design does not say the worker sets protection again before it receives the next message. A message that arrives after release but before the scale-in stop is received unprotected, and a stop then sends visibility 0, which dead-letters the event. The sentence "it cannot catch a task between two messages" is therefore too strong. State that protection is set before every receive (and the worker does not receive when setting it fails), or that the worker stops polling once protection is released.

> R-06 Reviewer note: Fixed: message group id imports, FIFO dead-letter queue, standard event dead-letter queue, queue policy limited to the rule, SSE-SQS, 14-day retention. Still open: (1) the design says the rule target sets the deduplication id from the event id, but an EventBridge rule target for a FIFO queue carries only a message group id (the AWS target parameters show no deduplication field); name content-based deduplication on the queue, or Pipes, as the mechanism. (2) The design still does not say what a duplicate event does. BR4.1 is checked only at the keep step (functional-spec.md, keeping to removing), so a resent event for a stored model downloads and scans the whole model, then fails with a failure email. State this as accepted, or add an early marker check before the download.

> R-07 Reviewer note: The deny is limited to GetObject, PutObject, and DeleteObject, exempts the worker role, the CDK deploy and CloudFormation execution roles, and named administrator roles, and the deployment fails when the administrator setting is empty. The sentence about the task starter is gone. The Assumptions bullet still says the opposite (see the new stale-text finding).

> R-08 Reviewer note: scalability-design.md has a Transfer of the Wait from u2 to u1 section that names the queue as the delivery of FR1.5 and AC1.1.4, says u2 only verifies it, says no waiting status is needed, and lists the files to correct. The NFR2.3 text in scalability-requirements.md is reworded.

> R-09 Reviewer note: traceability.json now holds all 59 NFR identifiers of the unit (NFR1.1 to NFR1.9, NFR2.1 to NFR2.6, NFR3.1 to NFR3.16, NFR4.1 to NFR4.11, NFR5.1 to NFR5.10, NFR6.1 to NFR6.4), each with a target, and the NFR2.3 target refers to the transfer note.

> R-10 Reviewer note: Fixed: the allow-list now has matchesTotal, the metric envelope, and the per-phase durations; the copied keys are replaced by a count, the last key, and prefix-based removal, with the verification amended; the stuck alarm is stated to be outside the 15-minute target. Still open: logical-components.md, Component Inventory, row Holding area, still names the record as state/importId.json, while the reliability design and traceability use state/importId/record.json. Use one path.

> R-11 Reviewer note: The data path now says up to 4 files on local disk, bounded by the 20 GB check, and the memory budget is fixed: 4 files times 4 parts times 32 MiB is 0.5 GiB of upload buffers, inside the 4 GiB floor.

### Summary

The four Major gaps from iteration 1 are closed: the queue message has a full life cycle that always releases the group, the role list is exact and includes state, the completion marker cannot outlive its files, and the email limit has a durable counter with an alarm that can fire within minutes. Only Minor items remain, mainly the unprotected polling window after the idle release, the duplicate-event behaviour and deduplication mechanism, the old record path in the component inventory, and some leftover text. A developer can build this unit from the design as it stands.
