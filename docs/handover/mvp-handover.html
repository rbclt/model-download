1. What the MVP does

The application brings an open-weight model from the public Hugging Face site into your own Amazon S3 bucket, but only after it has been scanned for leaked secrets and personal data. It is event driven: nothing runs until an event names a model.

  1. A person or system puts an event on the model-import Amazon EventBridge bus. The event names a model (owner/name), an exact version (a 40-character commit hash), and the sender's email address.
  2. A worker running on AWS Fargate downloads every file of that version into a holding S3 bucket.
  3. The worker scans the files. Text and settings files are searched for secrets and personal data. Weight files are checked by their file type and, for .safetensors, by their header.
  4. A clean model is copied into the final S3 bucket. A _COMPLETE marker file is written last, so a model is complete only when the marker exists.
  5. If a download fails, the scan finds anything, the 6-hour limit passes, or the copy fails, everything the import created is removed and an email goes to the team mailbox and to the sender.

Every event ends in exactly one of five outcomes: stored, removed-with-email, removed-email-failed, rejected, or refused-already-stored (section 10).

Scope of this first version: public models only (no Hugging Face account or token), smaller models (up to 1,000 files and 20 GB; the typical case is about 16 GB), one import at a time, one environment (staging) in one AWS account and Region.

Read this first. The code and its automated tests are complete, but the application has never been deployed, the container image has never been built, and no real model, real AWS service, or real email has been used. The tests use stand-ins for S3, SQS, SES, and Hugging Face. Plan for a careful first deployment with a small model (section 8 and section 11).

2. How it works (architecture and flow)

The life of one import

  1. Start event. The bus rule start-import sends events with source = model.import and detail-type = ModelImportRequested to the FIFO queue. The queue hands out one message at a time, so imports never overlap.
  2. Worker starts. An alarm notices a waiting message and sets the Fargate service to 1 task (about 3 minutes). The worker receives the message, keeps it alive with a heartbeat every 5 minutes, and sets task protection so the platform does not stop it mid-import.
  3. Check the event. A bad event is rejected: nothing is downloaded and the team (and the sender, if the address is well formed) gets an email that names each failed field, never its value.
  4. Front door. If the outcome already exists, nothing is done. If a _COMPLETE marker for this model version already exists from another import, the event is refused (refused-already-stored).
  5. 6-hour clock starts when the worker takes the event off the queue (queue waiting time does not count).
  6. Download the file list from Hugging Face, check the limits (at most 1,000 files and 20 GiB), then download up to 4 files in parallel to holding/<importId>/. Each download is checked for size and hash, and retried up to 3 times (waits of 5, 10, 20 seconds; at most 30 minutes of waiting in total).
  7. Scan (section 5). Any finding fails the whole import.
  8. Keep. Copy every file server-side to models/<owner/name, lowercase>/<version>/, write _COMPLETE last, then empty the holding folder. Once the marker is written, nothing can undo the model.
  9. Remove (on failure). Delete the marker first (if it is this import's), then every file the import created, then list again to prove nothing is left. Anything still found is reported as a "leftover".
  10. Finish. Email (on failure), one import_outcome log line, the one-time outcome object, and the final record. The message is deleted from the queue only after the outcome exists.

4. Inputs

4.1 The start event (contract C1)

{
  "source": "model.import",
  "detail-type": "ModelImportRequested",
  "detail": {
    "modelName": "owner/name",
    "exactVersion": "<40 characters of 0-9 and a-f>",
    "senderEmail": "person@example.com"
  }
}
FieldRule
modelNameowner/name; letters, digits, dot, underscore and hyphen only. A name with one part (no owner/) is rejected
exactVersionThe full 40-character commit hash (lower-case hex), not a branch or tag
senderEmailOne plain email address. It receives the failure email, so it should be a real mailbox that SES may send to
  • An event that fails these checks is rejected: no download, an email naming the failed fields, outcome rejected.
  • A message that is not a start event at all (wrong source or detail-type, unreadable body) gets no email and no outcome. It is logged as event_rejected and deleted.
  • The sender needs permission to call events:PutEvents on the bus. The bus itself accepts only principals of the same account.

5. What the scan checks

Any single finding fails the whole import. There is no way to accept a finding in this version. A finding records the file name, the place, and the kind. It never records the matched text, any part of it, or the text around it.

File classWhich filesWhat happens
Text and settingsEndings json, jsonl, txt, md, yaml, yml, py, jinja, toml, cfg, ini, csv, tiktoken, and files with no endingRead in 1 MiB parts and searched with the patterns below
Weight (allowed).safetensorsContent not scanned; the header length and header are checked
Weight (not allowed)bin, pt, pth, pkl, pickle, ckpt, h5, onnx, gguf, msgpack, npzA finding "disallowed weight type" (these formats can carry executable code or cannot be read safely)
Other endingsAnything elseKept, not scanned (an owner decision recorded in the design)

Patterns (the smallest set for the first version; a pattern may be added, none removed): cloud access keys (AKIA/ASIA keys), private key blocks, tokens (for example hf_, ghp_, github_pat_, xoxb-, sk-, and JSON web tokens), passwords and secrets assigned in text, email addresses, phone numbers, government-ID-style numbers (nnn-nn-nnnn), and street addresses. Up to 100 findings are recorded per file.

8. Package and deploy

8.1 How the application is packaged

  • Python package: pip install . installs the model_import package and the command model-import-worker (entry point model_import.worker:main).
  • Container image: built from the Dockerfile at the project root. Base image python:3.12-slim (the build argument BASE_IMAGE can replace it), runs as the non-root user worker, entry point model-import-worker. Only pyproject.toml and src/ go into the build context (.dockerignore).
  • You do not push the image yourself. cdk deploy builds it (platform linux/amd64) and publishes it to the repository that cdk bootstrap created, then points the Fargate task at it. This needs Docker running on the deploying machine.

To try the image build on its own (not yet done on any machine):

docker build -t model-import:local .
The stack builds the image without passing a base-image digest, so every build starts from the tag python:3.12-slim and the base image can change between builds. Pinning it by digest needs a small stack change (add build_args in infra/model_import_stack.py, function _asset_image).

8.2 First deployment, step by step

  1. Sign in to the AWS account (for example aws sso login --profile <profile>) and select us-east-1.
  2. Install the CDK command line: npm install -g aws-cdk.
  3. Bootstrap once: 
    cdk bootstrap aws://<account-id>/us-east-1
  4. Set the deployment settings. Either in the environment: 
    $env:MODEL_IMPORT_TEAM_ADDRESS = "team@example.com"
$env:MODEL_IMPORT_SENDER_ADDRESS = "sender@example.com"
$env:MODEL_IMPORT_BREAK_GLASS_ROLE_ARNS = "arn:aws:iam::<account-id>:role/<admin-role>"
    or as -c options on the commands below.
  5. Look before you deploy. Synthesis shows the template and any setting problem: 
    cdk synth
cdk diff
  6. Deploy: 
    cdk deploy
    It prints the IAM changes for approval. The first deployment builds the image, which takes a few minutes. Keep the stack outputs: EventBusName, ImportQueueUrl, HoldingBucketName, FinalBucketName, AlertTopicArn.
  7. Confirm the SNS subscription: open the email SNS sent to the team mailbox and click the link. Until then no alert reaches anyone.
  8. Check SES: the sender identity must be verified, and while in the sandbox the recipients too. Send a test email from the console to the team mailbox.
  9. (Optional) activate the cost allocation tag app once in the Billing console so the budget is filtered to this application. Until then it measures the whole account.
  10. Run the first import with a small model (section 9) and watch the logs.

8.3 Deploying a change

  1. Make the change; run the checks in section 7 (all must pass).
  2. Make sure no import is running: the service desired count is 0 and the queue is empty (the deployment sets maximum healthy percent to 100, so a new task is never started beside a running one, and a running import is protected from being stopped).
  3. Run cdk diff, then cdk deploy. CloudFormation rolls back a failed update by itself; the buckets are never touched by a rollback.
  4. Send a test event for a small model.
Removing the stack. Both buckets have a "retain" removal policy, so cdk destroy leaves them (and the models) in place. Delete them by hand only on purpose.

9.1 Send a test event

Use a small public model. The hash below is only an example: use the real 40-character commit hash of the version you want.

aws events put-events --region us-east-1 --entries file://event.json

with event.json:

[
  {
    "EventBusName": "model-import",
    "Source": "model.import",
    "DetailType": "ModelImportRequested",
    "Detail": "{\"modelName\":\"owner/name\",\"exactVersion\":\"0123456789abcdef0123456789abcdef01234567\",\"senderEmail\":\"person@example.com\"}"
  }
]

The first task starts about 3 minutes after the event reaches the queue. A clean small model should end in stored within minutes; a 16 GB model is expected to take about an hour (a design target, not yet measured).

9.2 Read the result

  1. Logs: CloudWatch log group /model-import/worker. Every line is one JSON object. The result line is "event": "import_outcome". Example Logs Insights query for one import: 
    fields @timestamp, event, status, step, outcome, reason
| filter importId = "imp-..."
| sort @timestamp asc
  2. The final bucket: a stored model is at models/<lower-case owner/name>/<exactVersion>/<path>. It is complete only if _COMPLETE exists in that folder. Read only the files the marker lists.
  3. The record and the outcome in the holding bucket under state/<importId>/ (section 10.3).
  4. Email: failures email the team mailbox and the sender.

The marker is JSON: importId, modelName, exactVersion, files (each with path and sizeBytes), and completedAt. It holds no sender address.

10. Operate: alerts, logs, records, and recovery

10.1 The five outcomes

OutcomeWhat happenedWhat it means for you
storedScan clean, every file copied, marker writtenThe model is in the final bucket. No email. It may carry removalComplete: false if the holding folder could not be fully deleted (alert b fires; remove the leftovers by hand)
removed-with-emailThe import failed (download problem, finding, time limit, failed copy, other step). Everything was removed and every email was acceptedThe sender and team were told why. Nothing should be left
removed-email-failedFailed and removed, but at least one email was not accepted (SES refused it or a daily limit was reached)Files are removed, but someone may not know. Read emailSent and recipientsNotReached in the outcome. Alert (a) fires
rejectedThe start event had a missing or malformed field. Nothing was downloadedAn email names the failed fields (never values). Send a corrected event
refused-already-storedThat model version already has a _COMPLETE marker from another import, or a marker that cannot be readNo new import is needed. The sender and team were told

Once the _COMPLETE marker is written, nothing that follows can remove the model or change its outcome from stored.

10.2 Alerts

All alarms notify the SNS topic model-import-alerts (the team mailbox). Alarm names are as created in the stack.

AlertNameFires when, and what to do
(a)model-import-a-failure-email-not-sentAn email did not reach everyone (emailSent = false). Open the import's outcome; tell the people concerned by hand
(b)model-import-b-removal-not-completeFiles of a failed import may still be in the buckets (removalComplete = false). Remove them by hand (the failure email lists up to 20 leftovers; the logs have one leftover line each)
(c)rule model-import-c-worker-stoppedA worker task stopped with a non-zero exit code or failed to start (for example an image pull error). Look at the task's stop reason and the logs
(d)model-import-d-event-dead-letter-queue, model-import-d-import-dead-letter-queue, model-import-d-import-dead-letter-reminderA start event could not be queued, or an import stopped unexpectedly (message in import-dlq.fifo); the reminder repeats after 60 minutes. See 10.4
(e)model-import-e-email-limit-reachedA daily email limit was reached (30 failure emails, or 20 rejection/already-stored emails, per UTC day). Find the cause (often a burst of bad events)
(f)SES configuration set model-importA bounce or complaint. Check the sender and recipient addresses
stuckmodel-import-stuck-oldest-messageThe oldest message in the queue is over 10 hours old (a message can wait up to 7 hours behind a running import). Check the worker and the scale-out alarm
costBudget model-import-monthlyMonthly spend reached the limit (default 100 US dollars)

10.3 Reading a record and an outcome

Both are JSON objects in the holding bucket under state/<importId>/. They are history only (nothing reads them to decide what to do next) and expire after 30 days. The importId is imp- followed by the first 32 hex characters of the SHA-256 of the event id that the bus gave the event:

python -c "import hashlib,sys; print('imp-' + hashlib.sha256(sys.argv[1].encode('utf-8')).hexdigest()[:32])" <eventId>
ObjectKey fields
record.json (rewritten before each step)status and step (downloading, scanning, keeping, removing, done), modelName, exactVersion, startedAt, updatedAt, filesCopied, lastKeyCopied, outcome, failureReason, findings (at most 200; file name, place, kind; never values), findingsTotal
outcome.json (written once, never changed)outcome, removalComplete, finishedAt, failureReason, emailSent, recipientsNotReached (roles sender/team, never addresses)

If the outcome object exists, the import is finished; receiving the same message again does nothing.

10.4 When an import stops unexpectedly

If the worker stops in the middle of an import (task stopped, the 7-hour watchdog, a fatal error), the import is not cleaned up by itself. The message moves to import-dlq.fifo and alerts (d) fire. A person recovers it:

  1. Compute the importId and read state/<importId>/record.json. If outcome.json exists, nothing needs recovery.
  2. If the step was keeping or removing, look in the final bucket under models/<owner/name>/<version>/. A folder without _COMPLETE is not a stored model; its files never expire, so remove them by hand or run the import again.
  3. If the folder has a _COMPLETE whose importId is the one you are recovering, the model is stored; redriving the message finishes it as stored with no email.
  4. Files under holding/<importId>/ expire after 2 days; unfinished uploads are aborted after 1 day.
  5. Fix the cause, then in the SQS console open import-dlq.fifo and choose "Start DLQ redrive". A redriven message gets a new 6-hour clock.

A failed import that ended with an email is recovered by sending the same start event again after the cause is fixed. If the email says the removal was not complete, remove the listed leftovers by hand.

10.5 Limits worth knowing

  • Email limits (per UTC day, fixed in the code): 30 failure emails and 20 rejection/already-stored emails. Past the limit no email is sent, the event still ends with its outcome, and alert (e) fires.
  • The 6-hour limit is checked before each step and each file, at every download chunk, and at every part of a large copy. One copy call of up to 5 GiB, the scan of one text file (5 minutes), the removal, and the email cannot be interrupted, so the design aims at the import having stopped within 10 minutes after the deadline. It is never checked after the marker is written.
  • One import at a time. Other events wait in the queue. A second event for a model version that waits behind the first is refused once the first has stored it.
  • The limits and the email limits are constants in the code, not settings.

11.3 Known limits of the product

  • Single-name models (no owner/) are rejected. Any finding fails the whole import. Files with unknown endings are kept without being scanned.
  • An unexpected stop is recovered by a person, not automatically.
  • Only the Region us-east-1 and one stack per account are supported (fixed resource names).
  • The earlier idea of a 140 GB model path was dropped: this version is for smaller models.

12.3 Security design in brief

  • No secrets: the worker needs no password, key or token; nothing sensitive is in code or logs (the logger writes only allow-listed fields; findings never include matched text).
  • Hugging Face is reached over HTTPS only with certificate checks and no credentials; downloaded files are checked for size and hash.
  • Both buckets are private, encrypted, TLS 1.2 or higher only, and object access is denied to everyone except the task role, the CDK roles and the break-glass roles (and the optional smoke-check role).
  • The event bus accepts events only from principals of the same account; the queue accepts messages only from the bus rule.
  • The task role has no s3:* and no Resource: *; the template tests check this.
  • Emails never contain a matched value, and the sender's address is never written to a log, record, outcome or marker.
